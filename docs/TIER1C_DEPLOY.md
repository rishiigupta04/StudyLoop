# Tier 1c — shipping the ONNX intent bundle (Hugging Face → Docker build → Render)

How the trained classifier gets from `ml/saved_models/` (gitignored) onto Render, how to roll it back, and what
nobody has verified yet. Model, numbers and the CPU analysis: [`TIER1C_MODEL.md`](TIER1C_MODEL.md). Manual checks
after a deploy: [`TIER1C_SMOKE_TEST.md`](TIER1C_SMOKE_TEST.md), section "After the deploy (Render)".

## What ships and where

| piece | where | in git? | job |
|---|---|:-:|---|
| the bundle: `model.onnx` (INT8, 67.5 MB), `tokenizer.json`, `labels.json`, `calibration.json`, `meta.json` — 68.3 MB in all | `ml/saved_models/intent-onnx/<version>/` locally; a public Hugging Face **model repo** (default `rishiigupta04/studyloop-intent`, owner **not confirmed**) as the shipping copy; `/app/models/intent` in the image | no | what `onnx_classifier.py` loads (`INTENT_MODEL_DIR`, default `models/intent`) |
| model card (`README.md` on the Hub) | generated into the same Hub commit by `publish_bundle.py` | no | numbers computed from `meta.json`, `calibration.json`, `ml/reports/metrics.json`; says plainly that real speech is not measured yet |
| `backend/bundle.lock.json` | **under `backend/`**: `render.yaml` has `rootDir: backend`, so the Docker build context is `backend/` and a file under `ml/` would be invisible to the build | **yes** | `{schema, repo, revision, version, files: {name: {bytes, sha256}}}`; `revision: null` = not published yet |
| `backend/scripts/fetch_intent_bundle.py` | run by the Dockerfile, or by hand | **yes** | stdlib-only: downloads `<base-url>/<repo>/resolve/<revision>/<file>` (public repo, no token; Hub answers 302 to a CDN), checks size + sha256 of every file, moves them into place only if all pass, otherwise leaves nothing behind. `--verify-only` re-checks a directory against the lock |
| `ml/publish_bundle.py` | ML venv | **yes** | the producer: `--write-lock` (no network) and `--push` (uploads, proves the round trip, writes the lock) |

`backend/Dockerfile` order: `pip install` → `COPY bundle.lock.json` + `scripts/fetch_intent_bundle.py` → `RUN` the
fetcher → `COPY app` + `studyloop_nlp`. Editing app code therefore never re-downloads 68 MB (a changed
`requirements.txt`, lock or fetcher invalidates that layer, and a base-image bump does too), and **a failed fetch
fails the build**: Render keeps serving the previous deploy. `render.yaml` sets `CLASSIFIER=onnx`.

The `README.md` on the Hub is **owned by the generator**: every `--push` replaces it with a freshly generated card, so
do not edit it on huggingface.co. A licence for the weights, once chosen, goes into `build_model_card` in
`ml/publish_bundle.py` (with its test), not into the Hub's copy.

## First publish (once)

1. **Confirm the Hugging Face username.** `rishiigupta04/studyloop-intent` is a guess from the GitHub name. If the
   Hub username differs, pass `--repo <username>/studyloop-intent` to every command below (it is written into the
   lock; the Hub repo name itself is free to choose).
2. **Decide what you are making public.** The Hub keeps every commit, so read before the first push.
   - `ml/.venv/Scripts/python ml/publish_bundle.py --write-card card.md` writes the model card exactly as `--push`
     will upload it (no network). It opens by saying real speech is not measured yet, lists the synthetic-test numbers
     (computed from the files, never typed), and claims no licence for the weights. The caveat is the constant
     `REAL_SPEECH_CAVEAT` in `publish_bundle.py`: when the real-speech evaluation exists, change it and add its numbers.
   - Licences, none verifiable from this machine: the card says Apache-2.0 for the base model
     (`distilbert-base-uncased`) and names CLINC150 and SNIPS, the source of the out-of-scope negatives, without stating
     their licences. The header of `ml/download_oos.py` says CC BY 3.0 and CC0: check both at the source and add the
     attribution CC BY needs. The paraphrases were generated by Gemini, `qwen3.8-27b` and `gpt-oss-20b`: check each
     provider's terms on using outputs to train a model you then publish. Decide on a licence for the weights; the card
     has none.
3. **Create the repo and a token limited to it.** On huggingface.co create an empty **public** model repo with that
   name (the build downloads without a token, so private will not work). Then Settings → Access Tokens → a
   *fine-grained* token with **write** access to that one repo and nothing else. Not verified (there is no write token
   on the dev machine): `--push` also calls `create_repo(exist_ok=True)`; if the Hub answers 403 there for a
   repo-scoped token, allow repo creation for the first push only and replace the token afterwards.
4. **Put the token in the shell, nowhere else.** Bash: `read -rs HF_WRITE_TOKEN && export HF_WRITE_TOKEN` (paste,
   Enter; nothing lands in the shell history). PowerShell: `$env:HF_WRITE_TOKEN = "<token>"` (it will be in
   PSReadLine's history: clear that line afterwards). It is read from the environment only: there is no `--token`
   option (a mistyped one is rejected without echoing the value), it is never printed, logged, stored or written to a
   file, and it is stripped from the environment of the fetcher subprocess. Never put it in `backend/.env`, Render or
   Vercel (`ENV_REFERENCE.md`).
5. **Dry run, no network:**
   `ml/.venv/Scripts/python ml/publish_bundle.py --repo <owner>/studyloop-intent --write-lock`.
   Reads `saved_models/intent-onnx/LATEST` (or `--bundle <version|dir>`) and refuses a bundle that does not hold
   together: a missing file, `meta.json` version ≠ directory name, `model.onnx`/`tokenizer.json` not matching the
   sha256 in `meta.json`, no `tau`/`temperature`, labels disagreeing with `meta.json`. Writes
   `backend/bundle.lock.json` with `"revision": null`. Until step 6 fills the revision, a null lock in `backend/` makes
   `backend/tests/test_fetch_bundle.py::test_committed_lock_is_valid` fail, by design (a null revision fails the
   build); to only look at the result add `--lock <some other path>` and delete it afterwards.
6. **Publish:** `ml/.venv/Scripts/python ml/publish_bundle.py --repo <owner>/studyloop-intent --push`. It
   re-reads and hashes a staged copy of the bundle (so what is uploaded is exactly what the lock describes), builds
   the model card (and refuses if `ml/reports/metrics.json` is for another bundle: run `ml/evaluate.py` first),
   `create_repo(private=False, exist_ok=True)`, one `upload_folder` commit with the five files + `README.md`, takes the
   commit oid as the revision, then **runs `fetch_intent_bundle.py` against that revision with no token into a temp
   directory** and checks every file again. Only then is `backend/bundle.lock.json` rewritten with the revision. If
   anything fails after the commit exists, the message prints the revision and leaves the lock alone; fix the cause
   and re-run (identical files make no new commit, so the revision is the same).
7. `unset HF_WRITE_TOKEN` (PowerShell: `Remove-Item Env:HF_WRITE_TOKEN`) and delete the token on the Hub if you will
   not publish again soon.
8. **Commit `backend/bundle.lock.json`** (together with `fetch_intent_bundle.py`, the Dockerfile and `render.yaml`, on
   Rishi's go), push to GitHub, and Render rebuilds itself: about 8 minutes. **Never push the Dockerfile/`render.yaml`
   change without a lock that has a revision**: with `revision: null` the fetch step fails by design and the build
   fails.
9. Run "After the deploy (Render)" in `TIER1C_SMOKE_TEST.md`.

## Retrain and ship

1. Train, then `export_onnx.py` → `calibrate.py` → `install_bundle.py` → `evaluate.py` (refreshes
   `ml/reports/metrics.json`, which the model card is built from) as in `ml/README.md`. To ship the 3-block candidate
   instead, make it `LATEST` first (`TIER1C_MODEL.md`, "6 vs 3 blocks").
2. `publish_bundle.py --write-lock`: the lock's revision is kept only if repo, version **and every sha256/bytes** are
   unchanged; otherwise it goes back to `null`. A recalibration keeps the version string but changes
   `calibration.json`, so it counts as a new bundle (new Hub commit, new revision).
3. `publish_bundle.py --push` (steps 4 and 6 above), commit the lock and the regenerated `ml/reports/*`, push, wait
   for Render, run the post-deploy checks. The Hub keeps every earlier commit, which is what makes the rollback below
   a one-line change.

## Rollbacks

- **Fast, no rebuild: `CLASSIFIER=regex`.** Render dashboard → the service → Environment → set `CLASSIFIER` to `regex`
  and redeploy without rebuilding (if Render offers a choice, pick redeploy, not rebuild). The image still holds the
  bundle; `/health` then says `"classifier": "regex"` and the WS `ready` message agrees. Flip back to `onnx` the same
  way. The regex classifier is unchanged since Tier 0. Caveat: `render.yaml` carries `CLASSIFIER` as a fixed value, and
  Render synced `CORS_ORIGINS` from the blueprint on a push to main (session 5), so a dashboard override of
  `CLASSIFIER` may be reset the same way (not verified for this variable); to make the rollback durable commit
  `value: regex` in `render.yaml`. Separately, `onnx_classifier` falls back to the regex by itself
  when the bundle is missing or broken (`/health`: `regex (onnx failed: …)`).
- **Back to the previous model: revert the lock and rebuild.** `git revert` the commit that changed
  `backend/bundle.lock.json` (or restore the old file), push, Render rebuilds (about 8 minutes) and the fetch step
  pulls the older revision. Nothing is re-uploaded: the Hub still has it.

## What the Docker build step proves, and what is not verified

The fetch step proves, on Render's own build network: the pinned revision exists and is public, every file arrives
with the locked size and sha256 (a corrupted, replaced or force-pushed file cannot reach the image), and a lock that
is malformed or still `null` stops the build instead of shipping an image that silently serves the regex.

**Not verified:**
- **Docker is not installed on the dev machine: the Dockerfile has never been built here.** The first real build is
  on Render. What was run: the fetcher against a local HTTP server shaped like the Hub's `/resolve/` URLs
  (`backend/tests/test_fetch_bundle.py`, `ml/tests/test_publish_bundle.py`), and `--verify-only` against the real
  bundle and a lock written by `publish_bundle.py` with a placeholder revision patched in (a lock straight from
  `--write-lock` has `revision: null`, which the fetcher's strict validator rejects, `--verify-only` included).
- **`--push` has only run against a stand-in `huggingface_hub`**: no write token exists on this machine. The first
  real `--push` is also the first real download of the Hub's 302 → CDN path by the fetcher (it runs in step 6).
- onnxruntime / tokenizers / numpy wheels on `python:3.12-slim` and the image's final size and memory: not measured.
- Everything about Render's CPU and cold start (below) is a model on the dev laptop, not a measurement.

**Suggested once the Hub repo is public: a CI `docker-build` job**, so the image is built (and the fetcher run against
the real Hub) on every PR instead of first on Render. A sketch, untested:

```yaml
  docker:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t studyloop-api backend
      - run: |
          docker run -d --name api -p 8000:8000 -e ENV=dev -e REQUIRE_AUTH=false -e CLASSIFIER=onnx studyloop-api
          for i in $(seq 1 30); do curl -fs localhost:8000/health && break || sleep 2; done
          curl -s localhost:8000/health | python -c "import sys, json; d = json.load(sys.stdin); assert d['classifier'] == 'onnx', d"
```

## Cold start, memory and CPU on a 512 MB, 0.1-CPU instance

From `TIER1C_MODEL.md` / `ml/reports/serving_bench*.json` (this laptop; Render publishes no CPU speed):

| | 6 blocks (the `LATEST` bundle) | 3 blocks (candidate) |
|---|---:|---:|
| build download, once per new lock | 68.3 MB (model 67.5) | 46.6 MB (model 45.9) |
| RSS: backend app ~95 MB, plus the model | +110 MB | +86 MB |
| model load at startup (before the warm-up turn) | 0.35–0.6 s | 0.36 s |
| classify p50 / p95, uncapped | 5–6 / 11–12 ms | 3–4 / 6.5 ms |
| whole fast-path turn p95, uncapped | 18–19 ms | 13–14 ms |
| CFS 0.1-CPU model, whole turn p95: laptop speed / half of it | 108 / 307 ms | 104 / 207 ms |

- **Memory is not the worry** (~205 MB of 512 MB with 6 blocks). **CPU is**: at 0.1 CPU a request gets 10 ms of
  compute per 100 ms, so a fast-path turn that needs more than 10 ms spills into the next period (~90 ms each). The
  CO4 target is a server-side fast path under 150 ms; only a measurement on Render settles it.
- Model load runs in the lifespan, before the first turn; on a throttled core it is slower than 0.35–0.6 s (not
  measured). A free instance that idled and woke up also pays the process start and the warm-up turn on the first
  request: probe a warm instance, not the first call.
- A turn whose confidence is below the bundle's τ goes to `llm_router`: those turns are slower by the LLM call, not
  by the classifier, and how many there are depends on the served τ (routing tables in `TIER1C_MODEL.md`). The
  post-deploy measurement below reports the fast-path rows only.

## Post-deploy measurement

```bash
# a Supabase access token (JWT) of a signed-in user: REQUIRE_AUTH=true on Render. Keep it in a shell variable.
backend/.venv/Scripts/python ml/probe_ws.py --url wss://studyloop-api-58vj.onrender.com --token "$JWT" --repeat 5 \
    --out ml/reports/probe_render.json
```

`probe_ws.py` sends 14 commands (English, Hinglish, Hindi) × `--repeat` over `/ws/session` and prints the server's own
per-node timings: the `/health` classifier line, the `ready` classifier, a table, then `classify_intent: n=… p50 … p95 …`
and **`fast path (server): n=… p50 … p95 …`**, the CO4 figure (rows with route `fast` only). Add `--audio` to also push
each command through `/api/tts` → `/api/stt` (spends Sarvam credit). Run it two or three times on a warm instance
(hit `/health` first) and keep the worst p95.

Record the result in `TIER1C_MODEL.md` ("Serving cost": a "Render, measured" row for the shipped bundle: fast-path
p50/p95, classify p95, n, date, instance plan) and commit `ml/reports/probe_render.json` (health, per-turn results; it
contains no token). If the p95 is over 150 ms, the levers in order: the 3-block bundle; trimming the rest of the
fast-path turn (LangGraph, `normalize`, slot parsing are about 6 ms of CPU next to the classifier's 3–6 ms at p50);
a paid instance with a real CPU share. `INTENT_MODEL_THREADS` stays 1 on purpose.
