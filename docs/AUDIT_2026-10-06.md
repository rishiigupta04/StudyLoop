## Study page (live-demo centrepiece)

**Demo verdict: `ready_with_caveats`**

Ready with caveats, for a rehearsed 6-minute run on Chrome or Edge with the MIT 6.006 lecture, a headset mic and a pre-warmed backend. The pipeline is complete and honest about failures: fast path about 10 ms, grounded no-spoiler Q&A, semantic seek, voice notes, chapters, typecheck clean. It is not safe to improvise. No human has done a spoken pass since the WAV/Sarvam fix, the first mic press hits a permission race, PTT can stick after a window blur, a stalled LLM call can delay 'pause', the Q&A banner contradicts the spoiler toggle, and the gear opens a fake Settings page. Fix the small items, rehearse twice, stay on the script.

**Strengths**

- The fast path is deterministic and LLM-free: about 10-15 ms server-side with the ONNX classifier, a calibrated tau and a regex fallback. Backend tests (1231) and the 743-scenario voice corpus guard it, and `tsc --noEmit` exits 0 (ran).
- Failure states are honest and localized: named transcript failure reasons, Retry only when retryable, a playback-only mode, a retrieval-only 'most relevant moment' fallback when the LLM is down, and BM25 fallback when query embedding fails.
- The anti-spoiler design is coherent: a high-water mark in RAG, summaries and chapter blurbs, a visible toggle, citation chips that seek, and citations stripped from speech.
- Write-behind persistence keeps turns fast: notes are acked in under 200 ms with a background summary (user edit wins, delete-after-save handled), and resume is flushed every 20 s.
- Barge-in, ducking and cancel are wired end to end: a new press stops TTS, sends turn.cancel and unducks on every exit path.
- No debug leakage: window.__studyloopSay is gated on import.meta.env.DEV and so is stripped from production builds, /collect is flag-gated, Quiz and XP sit behind DEMO_PREVIEW, and there are no TODO/FIXME markers in src.
- Auth is sound: the WS closes 4401 into a 'Sign in again' chip, DB writes use the server-side key with per-user filters, and secrets stay server-side.

- **SP-06** `high` · M · read — `backend/app/ws.py:291-302; services/llm.py:140-153,196-208; config.py:38`

**Demo script (about 6 minutes)**

1. 0:00 (30 s) Setup and framing. The study page is open on MIT 6.006 L1 at about 26:00, paused, EN, 'Voice ready' green. Say: 'StudyLoop turns a long lecture into something you talk to: hold ~ and speak English, Hindi or Hinglish.' Point at the chips: voice server, spoiler switch, language.
2. 0:30 (40 s) Fast path. Hold ~: 'pause', then 'go back thirty seconds', then 'speed one point five'. Point at the modal chips (Fast path, server about 10 ms, speech: sarvam). Say: 'A trained DistilBERT classifier on CPU decides this in milliseconds, with no LLM involved.' Skip the pipeline step list; it is only an animation.
3. 1:10 (30 s) Natural phrasing and undo. 'say that again', then 'go back to where I was'. One line: 'Handles natural phrasing and undo of voice jumps.'

## Backend production-readiness

**Demo verdict: `ready_with_caveats`**

Demo-ready with caveats; not production-ready. Auth and per-user scoping are sound: every REST route and the WebSocket verify the JWT, every row query filters on the verified user_id, and I found no IDOR. Degradation paths are well designed. The gaps are operational: no rate limits or quotas on credit-metered endpoints. An unbounded in-memory checkpoint store (measured 48 KB per turn, never evicted) that one user can use to OOM the 512 MB box. A shared thread pool that slow LLM turns can starve. No deploy gate, no retention or deletion for raw speech, and almost no observability. For a supervised demo: pre-ingest the videos, warm the instance, confirm credits and REQUIRE_AUTH, and do not push to main beforehand.

**Strengths**

- Auth is one shared resolve_user for REST and WS (auth.py:64-71): a presented token is always verified, even in anonymous mode, with an algorithm allowlist and an audience check; every router uses Depends(current_user).
- Every repository query filters on the verified user_id (notes.py:202,218; library.py:167,188,197,209; sessions.py:98) and video ids are regex-validated before reaching PostgREST params. I found no IDOR on notes, library, dashboard, chats or sessions.
- Ingestion claims rows with a conditional UPDATE (no double fetch across tabs or instances), caches results so a video costs one credit, and resumes a failed embed without re-buying the transcript.
- Failure handling is graceful throughout: regex fallback if ONNX fails, memory checkpointer if Postgres fails, Groq to Gemini to template, BM25 if embeddings fail, browser voice if STT/TTS fail. Every outbound call has an explicit timeout (JWKS 5 s, STT 8 s, TTS 15 s, embed 30/8 s, LLM 30 s, TranscriptAPI 60 s, PostgREST 5-15 s).
- RLS is enabled on all tables including the LangGraph tables (checkpointer.py:73-75). The service key and .env stay server-side and .env is gitignored. CI scans the client bundle for key shapes. The tool surface is minimal (player control, seek and note, with client-side effects only) and the RAG agent has no tools.
- 1,231 backend tests with a hermetic conftest that blanks every real key and URL; I ran my WS and auth probes through the same pattern without network.

## Tier 3 design (auto-quizzes and the rest)

Tier 3 #1 (chapter quizzes) is cheap enough and fits the architecture as a REST feature outside the voice graph. It needs a new migration, a model-quota decision and a human review of the Hindi questions before it is shown live. Tier 3 #2 and #3 should wait for the real-speech data, and vision and creator analytics should be dropped. There is no Quiz page or route today: only a mock dashboard widget (AIQuizWidget), a fake GamificationContext and a Sidebar XP banner, all hidden by VITE_DEMO_PREVIEW.

**Recommendation.** Build Q1 to Q4 (about 1.5 to 2 weeks) as REST plus a Quiz tab. Questions are generated lazily per (video, language, chapter) from raw transcript segments, delivered only once the chapter end is reached, and graded server-side. Ship Q5 (flag a wrong question, pre-generate and Hindi-review the demo lectures) before any live demo, and Q6 (voice answers) after. Ship no XP or streak until it is derived from a server ledger (Q7). Defer the in-browser classifier and the joint intent+slot model until real speech exists, and drop vision and creator analytics.

### Quiz design

**data model.** New backend/migrations/002_quiz.sql, run by hand in the Supabase SQL editor like 001. Three tables. quiz_sets: id, video_id, lang (en|hi), chapter_start_s, chapter_end_s, title, outline_at (the outline doc's `at` it was built from), covers_to_s, status (generating|ready|failed|none), error, model, prompt_v, usage_chars; unique(video_id, lang, chapter_start_s, outline_at). quiz_questions: id uuid, set_id, ord, kind ('mcq'), question, options jsonb (4), answer_idx, explanation, evidence_t, evidence_quote, flags, hidden. quiz_attempts: user_id, question_id, attempt_no, choice, correct, first_try, via (tap|voice|typed), created_at; unique(user_id, question_id, attempt_no). Keyed by outline_at because the EN and HI outlines are separate LLM runs (outline.py:320-345) whose chapter boundaries differ, and a re-run or OUTLINE_VERSION bump (video_repo.py:42) changes them; stale sets are kept (attempts reference them) but never served. RLS on all three with no select policy on sets/questions, because `videos` is readable by every authenticated user (001_init.sql:172) and quiz answers must not live in videos.chapters (that jsonb also rides every video.status event, ingest.py:62). Attempts: select-own only; every write goes through the backend service key, like interaction_logs. Sets are shared across users (like the outline cache); only attempts are per user. If the tables are missing the API reports enabled:false instead of erroring.

**generation.** Lazy, not eager: generate per (video, lang, chapter) when the client prefetches at ~60% of the active chapter or the learner opens the Quiz tab, so only the language actually used is paid for, and a concurrent claim is one INSERT ... ON CONFLICT DO NOTHING (stale 'generating' reclaimed after ~5 min, like claim_outline). Context = transcript_segments with start in [chapter.start_s, chapter.end_s), not chunks, because chunks overlap ~10 s into the next chapter (chunker.py:3) and would leak future content; capped at ~12K chars. Prompt contract, JSON only: {questions:[{q, options[4], answer, why, t:'m:ss', quote, key}]} with rules: answerable from this passage alone, never 'at 12:30 the speaker says', test understanding rather than names, plausible same-length distractors, exactly one correct, options <= 80 chars (voice-readable), n = clamp(round(minutes/2.5), 2, 4); 'quote' and 'key' are copied verbatim in the transcript's language. Validation (all free): parse with outline.parse_json; 4 options distinct after normalize(); answer index in range; t inside the chapter; quote found in the segments around t after studyloop_nlp.normalize() on both sides (script-agnostic, token overlap >= 0.85 to tolerate ASR noise); key inside quote; the question text does not contain the answer; deterministic per-user option shuffle (also cancels the LLM's index bias). Fewer than 2 survivors means status 'none' and an honest 'no quiz for this chapter'. Optional later (Q5): a blind-solve check where the fast model sees only quote + question + options and must pick the key, dropping disagreements (the ml/ judge precedent was 97.9% agreement). Hindi: reuse outline's Hindi clause (Devanagari with technical terms kept in Latin, outline.py:149-152) and the same 429 waits (_call); evidence stays in the transcript language, so an English transcript with Hindi questions is still checkable. Known weak spot: Hindi technical-term transliteration (TIER2_SMOKE_TEST.md:62-63), so the Hindi questions of the demo lectures need a human pass.

Each question is followed by immediate feedback: the explanation, the verbatim quote and a 'Rewatch [mm:ss]' seek link (always inside the watched chapter), plus an 'AI-generated, report a wrong question' link. Voice: do NOT touch the frozen 14-intent taxonomy or the graph. STT variants 'bee/see/dee', 'option two', 'second one', 'dusra/doosra', Devanagari ordinals, or a strong fuzzy match to one option) answers {matched:true,...} or {matched:false}, and a miss, or any hit by a player intent in regex_classifier, falls through to the normal sendUtterance. ### Risks

- A wrong or ambiguous generated question (worst in Hindi) in a live demo is worse than no quiz: mitigated by validation, a flag button, and a mandatory human review of the pre-generated demo lectures (Q5); the Hindi transliteration weakness is already documented (TIER2_SMOKE_TEST.md:62-63).
- Quiz generation draws on the same Groq gpt-oss quota as the live router and Q&A, which memory says must not be used for bulk work without Rishi's OK; an unguarded burst could starve live voice turns.
- Chapter lists differ per language and change when the outline is regenerated (OUTLINE_VERSION bump or retry), so sets must be keyed by outline_at and old sets orphaned, not re-pointed.
- max_watched_s is client-asserted and rises on seek-then-play (useYouTubePlayer.ts:154), and the Transcript tab shows the whole transcript, so quiz gating and any XP built on it are a nudge, not a guarantee.
- Quiz content must never go into videos.chapters or any table with a select policy for authenticated users: 001_init.sql:172 lets every signed-in user read videos, which would expose answers.
- The migration is a manual SQL-editor step on Supabase, so a deploy before Rishi runs 002_quiz.sql must degrade to enabled:false and hide the tab rather than error.
- Free-tier rate limits (429 and tokens-per-minute) already hit the outline job, so quiz requests must stay small and reuse the 429 waits; a daily budget can run out mid-demo, hence pre-generation.
- Tier 3 #3 is easy to over-sell: hosted STT already crosses the network to the same Render instance, so the in-browser classifier would not remove cold-start dependence, and it moves the CO4 latency metric from server-side to client-side.
- The Wong et al. 2024 reference exists in the repo only as one roadmap line pointing at a Business Need doc that is not in the repo, so any effect-size claim in UI or report copy would be unsupported.
